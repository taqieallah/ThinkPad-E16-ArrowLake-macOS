## 1. What was checked and how

* `symbols.txt` gives 850 `(__TEXT,__text)` symbols; the disassembly gives 20,936
  instructions covering `0x14898600..0x148ab563` with no gaps and zero bytes that
  disagree with the Mach-O (checked instruction-by-instruction against the file).
* `taint.py` runs a flow-sensitive abstract interpretation over every function:
  it tags `this`, tracks the three known MMIO struct fields, register copies,
  `lea`/`add` address arithmetic, stack spills and branch merges, and reports every
  memory operand whose base register carries a BAR0 register-base tag.
* `liveness.py` computes register/flag liveness (conservative for calls: a callee may
  read all six integer argument registers) to derive each stub contract.
* `verify-sites.py` re-reads the Mach-O, re-runs `llvm-objdump`, re-parses `apv.dis`,
  and asserts the whole table (592 assertions) without using any generator code.

## 2. The three MMIO setup paths — confirmed, with one naming correction

All three classes do exactly the same two-step mapping:
`mapDeviceMemoryWithRegister(0x10, 0)` (IOPCIDevice vtable slot **0x908**), then
`getVirtualAddress()` on the returned `IOMemoryMap` (IOPCIMMIO vtable slot **0x118**),
then `+ 0x1000`.

> **Correction to the working notes:** the struct field that holds the *BAR base*
> is **not** the `+0x168 / +0xe28 / +0x2a8` slot. Those slots hold the **virtual
> address of BAR0 + 0x1000**, i.e. the *register base*. The `IOMemoryMap` object
> itself is kept at `+0x160 / +0xe20 / +0x2a0` and is what `free()`/`teardownDevice()`
> release. Therefore every access shape is `[regbase + disp]` with
> `BAR0 register offset = disp + 0x1000` (not `disp - 0x1000`), and the prior list
> annotations are correct.


### 4.1 Specific corrections

1. **`__TEXT+0x2f67` is not a BAR access.** Bytes `ff 90 e0 08 00 00` decode to
   `callq *0x8e0(%rax)` where `%rax` is the `IOPCIDevice` vtable obtained from
   `0xdd8(%rbx)` in `AppleParavirtAccelerator::configureDevice`. `%esi=5` is the PCI
   capability id (MSI), so this is the capability-lookup vtable call. **Do not patch.**
2. **`__TEXT+0x2CDC` is two instructions, not one.** `89 4a 34` is
   `movl %ecx,0x34(%rdx)` (write BAR0+0x1034) and `44 8b 62 34` is
   `movl 0x34(%rdx),%r12d` (read back BAR0+0x1034). The prior list is not wrong, but
   a patch must treat them as one 7-byte span; patching only the write would leave
   the device read to the shadow RAM (wrong negotiated version), and patching only
   the 4-byte read is impossible under the 5-byte rule without also consuming the
   following 7-byte store (alternative given in §7.8).
3. **`__TEXT+0x10AA`** loads `this+0x168` (the register base that already equals
   BAR0+0x1000) and reads `+0x22c`, i.e. BAR0+0x122c — the prior annotation is right.
   It is the only read of the display-port-count register; the driver never writes it.

## 5. Coverage: are there BAR0 accesses outside the list?

**No. The 19 BAR0 instructions in §3 are the complete set in this kext.**
The argument, in decreasing strength:

1. BAR0 can only be reached through the three `mapDeviceMemoryWithRegister(0x10,0)`
   calls; those are the only three occurrences of vtable slot `0x908` in `__text`.
2. The mapping virtual address (+0x1000) is only stored to `this+0x168`, `this+0xe28`,
   `this+0x2a8`. Those slots are loaded 1 / 13 / 1 times: 10 of the 13 accelerator
   loads use an accelerator `this`, while 3 load `accel+0xe28` through an accelerator
   pointer reached from a display-pipe block (`dp+0x328`) or the virtual channel
   (`vc+0xf0`). All 15 are the rows of §2.1.
3. Every consumer uses the pointer in the same function, immediately. No register-
   base pointer escapes into another object field, into a callee argument, or onto the
   stack in a way that survives to another function (escape probe: only stale-register
   false positives at call sites that do not take that argument).
4. The specific areas requested were checked explicitly:
   * **display pipe / cursor**: the only BAR0 touch is the cursor-state write
     `BAR0+0x1220` (`__TEXT+0xcc60`) inside the `updateCursorState` block; the pipe
     object itself reaches it via `this+0x328` = accelerator, then `accel+0xe28`.
     `process_online/offline/enable/signalDisplay` do not touch BAR0.
   * **virtual channel / command queue**: `submitBuffer` and `resetHardwareAndReplay`
     write the two FIFO doorbells `BAR0+0x1020` / `BAR0+0x1028` through the accelerator
     held at `vc+0xf0`. Command submission itself goes through
     `AppleParavirtAccelerator::writeFifo` (sites S07/S08).
   * **interrupt / status**: the `setupInterrupts` action block is the only consumer of
     the status registers (S12/S13/S14); `handleFaultInterrupt` itself does not read BAR0.
   * **power state**: no PM function in `__text` references any of the three fields.
   * **EDID / I2C**: the `edid*` functions are pure buffer math over the EDID blob;
     no BAR0 access, no I2C path in this kext.
   * **DMA / descriptors / page tables / resource heap / command allocator**: all work
     on IOMemoryDescriptors and their own objects, never on BAR0.

## 6. Live-bring-up classification

Assumptions used for the decision, per the bring-up design:
(a) the 16 KiB BAR0 window is backed by a kernel RAM page shared with the userspace
daemon; (b) reads of registers that are **not device-computed** are correct from that
RAM; (c) writes are plain stores into the RAM, polled and applied by the daemon.

### 6.1 Reading of the rule for each patch-required site

* **S01 / BAR0+0x122c — display port count.** The host sets it; the guest never
  writes it. A shadow read yields 0, `Control::start` silently falls back to 1 port.
  Patch to a dispatched read (or, weaker, the daemon must pre-populate the shadow
  page *before* the kext starts, which is not guaranteed at boot).
* **S07 / BAR0+0x100c — FIFO cursor.** Device-side write cursor; polled in a loop by
  `writeFifo()`. Shadow read can spin forever or overwrite unconsumed commands.
* **S09+S10 / BAR0+0x1034 — version handshake.** Write-request then read-negotiated-
  version; the read value drives the retry loop. Must be one atomic dispatch
  (`versionPair`) against the Reims device.
* **S12 / BAR0+0x1018, S13 / BAR0+0x1014 — stamp / display pending flags.** Device-
  updated, consumed by the interrupt action block as a bitmap handed to
  `signalStamps`/`signalDisplays`; they are read-to-clear in the real GPU contract and
  a shadow copy would be permanently stale.
* **S14 / BAR0+0x102c — fault status.** Device-latched; non-zero must divert into
  `handleFaultInterrupt`. A shadow zero would silently disable fault recovery.
* **S16 / BAR0+0x1000 — FIFO disable on teardown.** Not a value question but an
  **ordering/ack** requirement: the very next steps release the FIFO descriptor/map
  and the BAR mapping. The daemon must have applied and acknowledged the disable
  before the kernel frees those pages, otherwise the still-running worker can touch
  freed memory. A plain shadow store cannot provide that completion signal.

Everything else is a pure guest-computed write (root/FIFO PFNs, FIFO length/start/
enable, doorbells, fallback version write, framebuffer start, cursor and channel
doorbells) and therefore needs no patch under assumptions (b)/(c). The only one that
deserves a second thought is `0x2df0` (fallback version force-write): see §7.9.

## 7. Patch plan — exact spans and register contracts

A patch is one 5-byte near `CALL rel32` followed by NOP padding to the end of the
span (`66 90` for a 2-byte remainder, `90` for 1). The call target must be a kernel
stub within ±2 GiB of the site. The stub must behave exactly like the original
instructions except for the BAR0 side effect. Native kernel text is
`__TEXT`+offset; the corresponding VAs are given in `sites.json`. S10 (`0x2cdf`)
needs no separate patch: it is the second instruction of S09's 7-byte span.

### 7.1 S01 — `__TEXT+0x10aa` (`0x148990aa`) — BAR0 `0x122c`

```
span        : 7 bytes at __TEXT+0x10aa .. __TEXT+0x10b1 (VA 0x148990aa)
original    : 44 8b 88 2c 02 00 00
              __TEXT+0x10aa  44 8b 88 2c 02 00 00         movl	0x22c(%rax), %r9d
replacement : e8 xx xx xx xx 66 90
next boundary after span: __TEXT+0x10b1 (VA 0x148990b1)
entry regs  : bar0_register_base=%rax, this=%r14
outputs     : %r9d
flags after : dead (next instruction does not consume flags)
live after  : r14, r8, r9, rbx, rcx, rdx  (conservative liveness; stub must preserve these)
live at entry: r14, r8, rax, rbx, rcx, rdx
stub        : %r9d = apv_mmio_read(%rax, 0x122c, 4)
```

Notes: Single 7-byte instruction; call(5)+2-byte nop.

### 7.8 Alternative for the version read (if only the read is replaced)

If for some reason the write at `0x2cdc` must stay a plain store, the read at
`0x2cdf` cannot be patched alone: its instruction is only 4 bytes. The next
instruction boundary is reached after 11 bytes, i.e. a span `0x2cdf..0x2cea` =
`44 8b 62 34` (`movl 0x34(%rdx),%r12d`) + `44 89 a7 48 0f 00 00`
(`movl %r12d,0xf48(%rdi)`). That stub would have to perform the device read into
`%r12d` **and** reproduce `movl %r12d,0xf48(%rdi)`, with `%rdi`=this live and
`%r12d` set. Replacement would be `e8 xx xx xx xx` + six NOPs, ending at
`__TEXT+0x2cea`. The 7-byte pair span above is strictly simpler and preserves the
write/read ordering on the device.

### 7.9 The `0x2df0` fallback write (not patched, decision point)

`__TEXT+0x2df0` (`c7 42 34 06 00 00 80`, 7 bytes, `movl $0x80000006,0x34(%rdx)`)
is a pure write and needs no patch for memory semantics. However it is the last
point in `setupVersion` where a dead transport could be detected, and the earlier
project note says the binding should "cover it and return a real failure to
configureDevice when transport is down". If fail-closed behaviour is wanted, this
site can be dispatched too: single instruction, 7-byte span, entry `%rdx`=register
base, `%rdi`=this, immediate value `0x80000006`, no outputs, flags dead. This is a
design choice, not a correctness requirement of the shadow-RAM model.

## 8. Risks and caveats that decide whether this can ship

1. **Context of S12/S13/S14.** They run in the IOKit interrupt-event-source action
   block installed and enabled by `setupInterrupts` (vtable slots 0x140/0x150), i.e.
   workloop / secondary-interrupt context, not a sleepable thread. The dispatcher used
   there must not sleep/block on the userspace daemon. Either (a) it publishes a
   request into a lock-free ring and bounded-spins on a pre-armed reply slot that the
   daemon keeps polling (risky re-entrancy/window), or (b) the interrupt action only
   schedules a workloop/deferred task that performs the dispatcher read later. Option
   (b) changes the "value consumed" ordering; do not assume a normal blocking IOConnect
   call is legal here.
2. **S07 is a loop body.** One dispatcher call per poll iteration inside `writeFifo`,
   which is on every command submission. Budget for the round-trip cost, or have the
   dispatcher serve a daemon-maintained cursor snapshot and only force-refresh after a
   bounded number of spins.
3. **S09/S10 pair.** The dispatcher must execute the write and the read on the Reims
   device in that order, in one request, and return the read value. Splitting it into
   two calls re-opens the race the original code avoids by doing them back-to-back.
4. **S14 branch stub.** The span replaces `cmpl $0,0x2c(%rax)` *and* `je 0x1489af32`.
   The stub must discard the return address pushed by the patched CALL and jump to
   `__TEXT+0x2f26` (fault present -> epilogue + tail-jump to `handleFaultInterrupt`)
   or `__TEXT+0x2f32` (no fault -> epilogue + return). Both are the original branch
   targets. Stack must be exactly as the function expects at that point (no extra push).
5. **Flags.** A CALL itself does not modify RFLAGS, but the dispatcher does. S12/S13
   must leave ZF/PF/SF/CF/OF as `testl value,value`; pushfq/popfq or reproducing the
   `testl` in the stub both work. All other stubs may clobber flags because the next
   instruction overwrites them.
6. **Register transparency.** The live-after sets above are conservative (a callee may
   read all six SysV integer argument registers). The simplest safe stub saves every
   GPR it touches (push/pop) except the declared output register, and restores flags
   only where listed. The conservative live-after sets may include registers that are
   not actually read on every path (e.g. `%r8/%r9/%rcx/%rdx` look live only because a
   later indirect call could read argument registers); preserving them anyway costs a
   few push/pops in the stub and removes the whole class of ABI mistakes.
7. **Call reachability.** The patched 5-byte `CALL rel32` must reach the stub, so the
   stub must live within ±2 GiB of `0x1489xxxx`/`0x148a4xxx`; a stub placed in the
   same kext (or any kernel text near it) qualifies, a `__DATA`-only trampoline does not.
8. **Uncached-device semantics.** Today these addresses are PCI BAR memory; a shadow
   RAM page is cacheable normal memory. That is fine for the 11 plain load/store sites,
   and is precisely why the 7 read/handshake sites are routed through the dispatcher.
   Any barrier/`mfence` requirements the original device-memory accesses implied are
   the daemon-side implementation’s responsibility, not the patched kernel text.
9. **`__TEXT+0x2f67` must be left alone** — patching it would break
   `IOPCIDevice::configureDevice` capability lookup and probably panic the driver.
